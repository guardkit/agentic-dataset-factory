# Runbook: Upload a fine-tuned Gemma-4 MoE model to Hugging Face

**Purpose:** Take the artefacts produced by `RUNBOOK-architect-fine-tune.md` (or the equivalent tutor runbook) and publish them to the Hugging Face Hub as two repos per model: a **weights repo** (merged-16bit + LoRA adapter) and a **GGUF repo** (q4_k_m + BF16 split + Modelfile).
**Machine:** Dell DGX Spark GB10 (`promaxgb10-41b1`). Uploads are bandwidth-bound; run from the box that already holds the 49 GB merged weights, not over wifi from a laptop.
**Driver script:** `scripts/push_to_hf.py` (in this repo). Each subcommand maps to one phase below.
**Duration:** ~5-30 min wall-clock per artefact depending on upstream bandwidth. `hf_transfer` saturates a gigabit link.
**Prerequisite:** A successful fine-tune (`RUNBOOK-architect-fine-tune.md` Phase 5 has signed off on the artefacts — non-empty `lora-adapter/`, `merged-16bit/`, `gguf_gguf/`).
**Reproducibility:** Phrased for the architect-agent domain but Phases 0-6 are domain-agnostic. To re-use for another domain (e.g. `gcse-tutor`), change the **Inputs** block and add a `DomainSpec` entry in `scripts/push_to_hf.py` if one isn't present. Worked examples for both architect-agent and gcse-tutor are in the **Inputs** block.

```bash
# === ARCHITECT-AGENT (this runbook's worked example) ===
DOMAIN="architect-agent"

HF_OWNER="RichWoollcott"                            # confirm with `hf auth whoami` (case matters for some Hub APIs)
REPO_WEIGHTS="${HF_OWNER}/architect-agent-gemma4-26b-moe"
REPO_GGUF="${HF_OWNER}/architect-agent-gemma4-26b-moe-GGUF"

# === GCSE-TUTOR (re-run for the study tutor; uncomment & swap) ===
# DOMAIN="gcse-tutor"
# ARTEFACT_ROOT="$HOME/fine-tuning/output/gcse-tutor-gemma4-26b-moe-2026-04-18"
# REPO_WEIGHTS="${HF_OWNER}/gcse-tutor-gemma4-26b-moe"
# REPO_GGUF="${HF_OWNER}/gcse-tutor-gemma4-26b-moe-GGUF"

REPO_DIR="$HOME/Projects/appmilla_github/agentic-dataset-factory"

# Staging dir for rendered model cards. ARTEFACT_ROOT is root-owned (created
# by the Docker training container), so we cannot write inside it. Use a
# user-writable sibling under ~/fine-tuning/ instead.
STAGING="$HOME/fine-tuning/staging/${DOMAIN}"
mkdir -p "$STAGING"
```

The artefact tree the runbook expects (this matches what `train_gemma4_moe.py` produces):

```
$ARTEFACT_ROOT/
├── lora-adapter/           1.9 GB — adapter_model.safetensors + tokenizer + chat_template
├── merged-16bit/            49 GB — full base + LoRA merged, vLLM-ready
├── gguf/                    49 GB — duplicate safetensors copy (used only as GGUF conversion source — DO NOT upload, redundant with merged-16bit)
├── gguf_gguf/               18 GB — actual GGUF files: Q4_K_M, BF16 split (00001+00002), mmproj, Modelfile
├── checkpoint-*/                  — intermediate checkpoints (do NOT upload)
├── README.md                      — TRL-autogenerated; we overwrite with a richer card in Phase 1
└── train.log                      — training log; kept locally for provenance, not uploaded
```

## Phase 0: Pre-flight gates

Read-only. Run after every fine-tune, before any repo creation or upload.

### 0.1 Artefacts present and non-empty

```bash
for sub in lora-adapter merged-16bit gguf_gguf; do
    if [ ! -d "$ARTEFACT_ROOT/$sub" ] || [ -z "$(ls -A "$ARTEFACT_ROOT/$sub" 2>/dev/null)" ]; then
        echo "MISSING: $ARTEFACT_ROOT/$sub"; exit 1
    fi
done

# Spot-check the critical files
test -f "$ARTEFACT_ROOT/lora-adapter/adapter_model.safetensors" || { echo "MISSING adapter weights"; exit 1; }
test -f "$ARTEFACT_ROOT/merged-16bit/model.safetensors.index.json" 2>/dev/null \
    || ls "$ARTEFACT_ROOT/merged-16bit/"*.safetensors > /dev/null 2>&1 \
    || { echo "MISSING merged-16bit safetensors"; exit 1; }
ls "$ARTEFACT_ROOT/gguf_gguf/"*.gguf > /dev/null 2>&1 \
    || { echo "MISSING gguf files"; exit 1; }

echo "PASS — artefacts present"
du -sh "$ARTEFACT_ROOT"/{lora-adapter,merged-16bit,gguf_gguf}
```

Expected (architect-agent 2026-05-02 run):
- `lora-adapter`: 1.9 GB
- `merged-16bit`: 49 GB
- `gguf_gguf`: 18 GB

### 0.2 Disk free on the cache mount

The HF uploader copies files into `~/.cache/huggingface/hub/` during multipart staging. Need at least ~50 GB free on whichever mount holds that cache.

```bash
df -BG ~/.cache/huggingface/ | awk 'NR==2 {gsub("G","",$4); print; if ($4+0 < 60) print "WARN: <60GB free on HF cache mount"}'
```

### 0.3 HF auth configured with a *write* token

The login state in Firefox doesn't help us — the CLI needs its own token. If `hf auth whoami` errors or returns a read-only token, generate a write token at https://huggingface.co/settings/tokens and run `hf auth login`.

```bash
# Install deps if needed (one-shot, system-wide for the user)
pip install -U "huggingface_hub>=1.8" hf_transfer

hf auth whoami    # should print the username + a list of orgs
$PUSH whoami      # should match — confirms the same token the script will use
```

If `hf auth whoami` says "Not logged in":

```bash
hf auth login
# Paste a write token (https://huggingface.co/settings/tokens → "Create new token" → fine-grained, scope "Write access to all repos")
```

### 0.4 Repo-name sanity

| Check | What to do |
|---|---|
| HF_OWNER matches your actual username | `$PUSH whoami` — compare the `name` field |
| Repo IDs don't already exist as someone else's | Visit `https://huggingface.co/$REPO_WEIGHTS` in a browser — if it 404s, you're fine. If it exists and isn't yours, pick a different name. |
| You're comfortable with public visibility | Default is public; pass `--private` to `create-repo` if not |

### 0.5 Decision matrix

| All gates pass | → | Proceed to Phase 1 |
| Artefact missing or empty | → | **STOP**. Investigate the fine-tune output before uploading partial state |
| Token is read-only / not configured | → | **STOP**. `hf auth login` with a write token |
| Repo name collides with a stranger | → | **STOP**. Pick a different name and update the Inputs block |
| `gguf/` directory exists but `gguf_gguf/` doesn't | → | The script's `--skip-export` path was used. Export GGUF manually before this runbook, OR plan to upload weights only (skip Phase 4) |

## Phase 1: Generate model cards

The TRL autogenerated `README.md` is a one-liner. We replace it with a richer card that has intended-use, sample prompt, limitations, training-data summary, framework pins, and the correct Gemma license tag.

```bash
mkdir -p "$STAGING"

# Weights repo card (merged + adapter)
$PUSH render-card \
    --domain "$DOMAIN" \
    --repo-id "$REPO_WEIGHTS" \
    --out "$STAGING/README-weights.md"

# GGUF repo card — same template, points back at the weights repo
$PUSH render-card \
    --domain "$DOMAIN" \
    --repo-id "$REPO_GGUF" \
    --out "$STAGING/README-gguf.md"

head -40 "$STAGING/README-weights.md"
```

Eyeball the rendered card. If `intended_use`, `limitations`, or `training_data_summary` need refinement, edit them in `scripts/push_to_hf.py` (the `DomainSpec` for this domain) and re-render. The runbook intentionally keeps the source-of-truth in code, not in a template file, so the next domain inherits the same structure.

## Phase 2: Create the repos

Idempotent (`exist_ok=True`). Safe to re-run.

```bash
$PUSH create-repo --repo-id "$REPO_WEIGHTS"
$PUSH create-repo --repo-id "$REPO_GGUF"
```

For a dry run that prints what it would do without touching the Hub:

```bash
$PUSH create-repo --repo-id "$REPO_WEIGHTS" --dry-run
```

## Phase 3: Upload LoRA adapter (~1.9 GB, ~2 min)

Smallest artefact → upload first. Validates auth, chunking, and `hf_transfer` end-to-end before the 49 GB upload commits 30+ minutes of bandwidth.

```bash
# Adapter goes into a subfolder of the weights repo
$PUSH push \
    --repo-id "$REPO_WEIGHTS" \
    --src "$ARTEFACT_ROOT/lora-adapter" \
    --path-in-repo "lora-adapter" \
    --message "upload LoRA adapter"

# Verify the expected files landed
$PUSH verify --repo-id "$REPO_WEIGHTS" \
    --require "lora-adapter/adapter_config.json" \
              "lora-adapter/adapter_model.safetensors" \
              "lora-adapter/chat_template.jinja"
```

Expected upload speed: 50-100 MB/s with `hf_transfer` on a gigabit link. If you see <5 MB/s, `hf_transfer` is not active — check `pip show hf_transfer` and that `HF_HUB_ENABLE_HF_TRANSFER=1` is exported (the script sets it but a subshell may not inherit it).

---

## Phase 4: Upload merged-16bit weights (~49 GB, ~15-25 min)

Slowest single step. Detach into `tmux` or `screen` so an SSH drop doesn't kill it.

```bash
tmux new -s hf-push-weights "$PUSH push \
    --repo-id $REPO_WEIGHTS \
    --src $ARTEFACT_ROOT/merged-16bit \
    --include 'config.json' 'tokenizer*' 'processor*' 'chat_template*' 'special_tokens*' '*.safetensors' '*.safetensors.index.json' '*.txt' \
    --exclude '__pycache__/*' \
    --message 'upload merged-16bit weights'"

# Reattach: tmux attach -t hf-push-weights
# Detach:   Ctrl-B then D
```

The `--include` list is deliberate: it avoids uploading any stray `tokenizer.model` shards or `optimizer_states.pt` that some Unsloth versions leave behind, which would inflate the repo unnecessarily.

After the upload completes:

```bash
$PUSH verify --repo-id "$REPO_WEIGHTS" \
    --require "config.json" \
              "tokenizer_config.json" \
              "chat_template.jinja" \
              "model.safetensors.index.json" \
              "*.safetensors"
```

Push the model card last so it's not overwritten by anything in `merged-16bit/`:

```bash
$PUSH push \
    --repo-id "$REPO_WEIGHTS" \
    --src "$STAGING/README-weights.md" \
    --path-in-repo "README.md" \
    --message "add model card"
```

## Phase 5: Upload GGUF repo (~18 GB, ~7-12 min)

The GGUF repo is a separate user-facing artefact (llama.cpp / Ollama / on-device). Conventionally suffixed `-GGUF`.

```bash
tmux new -s hf-push-gguf "$PUSH push \
    --repo-id $REPO_GGUF \
    --src $ARTEFACT_ROOT/gguf_gguf \
    --include '*.gguf' 'Modelfile' \
    --message 'upload GGUF quantisations'"
```

After upload, write the GGUF repo card and verify:

```bash
$PUSH push \
    --repo-id "$REPO_GGUF" \
    --src "$STAGING/README-gguf.md" \
    --path-in-repo "README.md" \
    --message "add model card"

$PUSH verify --repo-id "$REPO_GGUF" \
    --require "*.Q4_K_M.gguf" "Modelfile" "README.md"
```

The card for the GGUF repo currently inherits the same template as the weights repo. If you want a llama.cpp-focused card (Ollama instructions, `llama.cpp` invocation, quant tradeoff table), add a `gguf=True` branch in `_CARD_TEMPLATE` and re-render — defer until you have a second domain wanting the same treatment to avoid premature templating.

## Phase 6: Post-upload verification

### 6.1 Web check

Open both repos in a browser:

```
https://huggingface.co/$REPO_WEIGHTS
https://huggingface.co/$REPO_GGUF
```

Check:
- Model card renders (no broken YAML frontmatter)
- "Files" tab shows all expected artefacts
- The base-model link in the card resolves
- License widget shows "gemma"
- Tags include `gemma-4`, `moe`, `unsloth`, `trl`, `lora`, and the domain slug

### 6.2 Download-and-load smoke test

The strongest "did this actually work" signal is a downstream load. From a clean Python env (NOT the upload-host's env, since that has the local files):

```bash
# On a different machine (e.g. your MacBook), or in a fresh venv with no local artefacts
python3 - <<PY
from huggingface_hub import hf_hub_download
p = hf_hub_download(repo_id="$REPO_WEIGHTS", filename="config.json")
print("config.json downloaded to:", p)
import json
print("model_type:", json.load(open(p))["model_type"])
PY
```

Expected: `model_type: gemma3` (or whatever the merged config reports — should match the base model's `config.json`).

If you have GPU available on a different box, the full load:

```python
from transformers import AutoTokenizer, AutoModelForCausalLM
import torch
m = AutoModelForCausalLM.from_pretrained("$REPO_WEIGHTS", torch_dtype=torch.bfloat16, device_map="cuda")
t = AutoTokenizer.from_pretrained("$REPO_WEIGHTS")
# Run the sample prompt from the model card
```

### 6.3 GGUF smoke

```bash
# On any box with llama.cpp installed
llama-cli -m <path-to-downloaded>/gemma-4-26b-a4b-it.Q4_K_M.gguf -p "Hello" -n 32
```

Or via `hf_hub_download`:

## Failure modes & recovery

| Symptom | Cause | Fix |
|---|---|---|
| `Hugging Face auth not configured` from any subcommand | No CLI token or token is read-only | `hf auth login` with a write token; re-run |
| Upload starts then stalls at ~0 KB/s | `hf_transfer` not active | `pip install -U hf_transfer`; export `HF_HUB_ENABLE_HF_TRANSFER=1` in the parent shell |
| `RepositoryNotFoundError` on push | Phase 2 was skipped or the repo ID has a typo | Re-run `create-repo`, then retry the push |
| Upload of merged-16bit fails partway through | Network blip; HF uploader is resumable | Re-run the same `push` command — already-uploaded files are skipped |
| `429 Too Many Requests` | HF rate-limit on a flurry of small files | Wait 30s, retry |
| `verify` reports a file missing but the upload reported success | Eventual-consistency lag on the Hub | Wait 30s, re-run `verify` |
| Card shows raw `{display_name}` in the browser | The card was written before `render-card` was re-run after editing the DomainSpec | Re-render and re-push the README only |
| Need to delete a repo you uploaded by mistake | Out of scope for this script (script never deletes); use the Hub web UI |

## Phase 7 (open / followup): Training-data upload

Deliberately **not** automated by this runbook. Reasons:

1. The dataset (`output/train.jsonl`, `output/rag_index/knowledge.jsonl`) was generated from source material whose license needs auditing before public release. The architect-agent corpus references DDD literature; the GCSE corpus may incorporate set-text quotations that fall outside fair use.
2. A separate `RUNBOOK-huggingface-dataset-upload.md` is the natural home once the legal review is done — it would push to `<owner>/<domain>-training-data` as an HF *dataset* repo (different repo_type), with a Dataset Card calling out provenance, schema (`messages`, `metadata.dimension`, `metadata.layer`, `metadata.type`), and the Player-Coach acceptance criteria.

Until that review happens, the **synthetic-pipeline source code** (this repo) is the published reproduction recipe, and the **weights** are the redistributable artefact.

## Quick-reference (all-in-one)

Once Phase 0 is green and Inputs are set:

```bash
# 1. Render cards
$PUSH render-card --domain "$DOMAIN" --repo-id "$REPO_WEIGHTS" \
    --out "$STAGING/README-weights.md"
$PUSH render-card --domain "$DOMAIN" --repo-id "$REPO_GGUF" \
    --out "$STAGING/README-gguf.md"

# 2. Create repos
$PUSH create-repo --repo-id "$REPO_WEIGHTS"
$PUSH create-repo --repo-id "$REPO_GGUF"

# 3. Upload adapter (small; smoke-tests auth + transfer)
$PUSH push --repo-id "$REPO_WEIGHTS" \
    --src "$ARTEFACT_ROOT/lora-adapter" --path-in-repo "lora-adapter"

# 4. Upload merged-16bit (long; in tmux)
tmux new -s hf-push-weights "$PUSH push --repo-id $REPO_WEIGHTS \
    --src $ARTEFACT_ROOT/merged-16bit \
    --include 'config.json' 'tokenizer*' 'processor*' 'chat_template*' 'special_tokens*' '*.safetensors' '*.safetensors.index.json' '*.txt'"

# 5. Upload GGUFs (in tmux)
tmux new -s hf-push-gguf "$PUSH push --repo-id $REPO_GGUF \

# 6. Push cards last
$PUSH push --repo-id "$REPO_WEIGHTS" \
    --src "$STAGING/README-weights.md" --path-in-repo "README.md"

```
