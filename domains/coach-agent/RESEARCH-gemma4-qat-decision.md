# Gemma-4-26B-A4B QAT fine-tuning — research decision record

> Produced 2026-06-19 by an adversarially-verified research workflow (10 agents, 6 research angles + 3 refutation passes + synthesis). Primary sources: unsloth.ai/docs, unsloth GitHub, huggingface.co model cards. Verdicts below are the adversarial fact-checks.

## Adversarial verdicts on the load-bearing claims

### REFUTED — unsloth/gemma-4-26B-A4B-it-qat-q4_0-unquantized can be loaded by Unsloth FastModel and LoRA-fine-tuned (16-bit LoRA) the same way as the bf16 unsloth/Gemma-4-26B-A4B-it base, on a 121GB GB10.

The claim asserts an equivalence ("the same way as the bf16 base") and is framed in the prompt context as the "presumed fine-tune entry" for the QAT path. No primary source supports that fine-tune-equivalence assertion; the strongest direct sources actively point the other way.

WHAT IS TRUE (so the claim is not pure fiction):
- Both repos exist. unsloth/gemma-4-26B-A4B-it-qat-q4_0-unquantized is real, tagged transformers/safetensors/gemma4, base_model google/gemma-4-26B-A4B-it, Apache-2.0. Its config.json reports architectures=["Gemma4ForConditionalGeneration"], model_type="gemma4", torch_dtype="bfloat16", and NO quantization_config. It ships full BF16 weights (model-00001/00002-of-00002.safetensors, ~51.6 GB). Architecturally it is identical to the -it base, so FastModel.from_pretrained would almost certainly LOAD it without error like any BF16 Gemma 4 checkpoint. Gemma 4 (released 2026-04-02) and its 26B A4B MoE (25.8B total / ~3.8B active) are genuine. So bare loadability is plausible.

WHY THE CLAIM IS REFUTED AS STATED:
1. Intended use contradicts it. The repo's own README and the Unsloth Gemma 4 / QAT docs describe these checkpoints verbatim as: "Unquantized QAT checkpoints (Q4_0): Half-precision weights extracted from the QAT pipeline, ideal for custom downstream compilation and research." Fine-tuning/FastModel/LoRA/training are NOT listed as an intended use anywhere on that page.
2. The canonical fine-tune entry is the OTHER repo. The official Unsloth Gemma 4 Fine-tuning Guide (unsloth.ai/docs/models/gemma-4/train) uses model_name = "unsloth/gemma-4-26B-A4B-it" (the plain BF16 -it base) and never references the qat-q4_0-unquantized repo as a fine-tune base. It advises LoRA (not full FT) and 16-bit/bf16 LoRA for this MoE, but bound to the -it repo, not the QAT one.
3. "The same way / same results" is unverified. QAT weights are deliberately conditioned so that POST-training int4 quantization preserves quality. Whether BF16-LoRA-tuning those QAT weights and then re-quantizing yields equivalent behavior to tuning the plain bf16 base is asserted by no primary source. The only affirmations that "you can fine-tune these with FastModel/LoRA" come from search-engine AI summaries and SEO blogs (gemma4.dev, lushbinary, etc.), which conflate the general FastModel capability with this specific repo and do not validate equivalence.

CONFIDENCE: High that no primary source validates the fine-tune-equivalence claim; high that the official guide points fine-tuning at the -it base instead; moderate that bare loading would technically succeed (architecture/dtype match, no quantization_config). Because the claim presents an unverified, contra-indicated path as an established equivalent capability, the correct verdict is refuted (it overstates). If the claim were narrowed to "FastModel can probably load these BF16 safetensors," that weaker form would be plausible/unknown — but that is not what was claimed.

### REFUTED — Fine-tuning FROM the QAT-unquantized checkpoint and exporting the LoRA-merged result to Q4_0 GGUF yields meaningfully better int4 serving quality than PTQ-quantizing a bf16-base fine-tune to int4 — i.e. the QAT path is worth the base swap for an int4-served model.

No primary source supports the claim's specific mechanism, and the most relevant primary source (Unsloth) directly contradicts its key step.

1) THE Q4_0 EXPORT STEP DESTROYS MOST OF THE QAT BENEFIT (decisive). Unsloth's Gemma 4 QAT documentation states verbatim for the exact model in question: "Converting to Q4_0 from QAT naively gets only 70.2% top-1 % accuracy for 26B-A4B" and that this is because the naive conversion "wasn't aligned with the BF16 QAT lattice." Quality is only recovered to 85.6% (+15.6%) by Unsloth's *dynamic* UD-Q4_K_XL method, NOT by plain Q4_0. Unsloth ships "only one GGUF file" per Gemma 4 model (UD-Q4_K_XL) precisely because they "found q4_0 to degrade accuracy despite being bigger." The claim explicitly names Q4_0 as the export target — i.e., the single path Unsloth identifies as the worst. So even the QAT base model loses ~15 points going to naive Q4_0; the claim's chosen serving format undercuts the very advantage it asserts.

2) A PLAIN bf16 LoRA FINE-TUNE + MERGE DOES NOT PRESERVE QAT INT4-ROBUSTNESS. The documented way to obtain a QAT int4 benefit in Unsloth is to run QAT DURING your own fine-tuning: set qat_scheme="int4" in get_peft_model, train with fake-quantization active, then quantize_(model, QATConfig(step="convert")) and export. Unsloth: "QAT simulates the true quantization procedure by 'fake quantizing' weights ... during training" and is "combined with LoRA fine-tuning." The academic literature (L4Q, QA-LoRA, QAT-with-LoRA) agrees the QAT advantage persists only when quantization is simulated during training and parameters are adjusted, not fixed. The claim's workflow (ordinary bf16 LoRA on top of a QAT checkpoint, merge, then naive PTQ to Q4_0) does none of this — merging perturbs weights off the QAT grid and the final requantization is effectively PTQ on a no-longer-QAT-aligned model.

3) NO PRIMARY SOURCE ENDORSES THE QAT CHECKPOINT AS A SUPERIOR FINE-TUNE ENTRY FOR INT4 SERVING. The HF model card for unsloth/gemma-4-26B-A4B-it-qat-q4_0-unquantized describes it only as "Half-precision weights extracted from the QAT pipeline, ideal for custom downstream compilation and research" — not as a fine-tune base that yields better int4 after merge+requantize. Google's blog claims QAT "yield[s] even higher overall quality compared to standard PTQ baselines" but provides NO numbers and refers to its own QAT-produced serving weights, not user-fine-tuned-then-PTQ models. The CONTEXT itself flags this as a "presumed fine-tune entry," and the presumption is unconfirmed.

CONFIDENCE: High that the claim as worded (Q4_0 export, base swap worth it) is refuted. The general statement "QAT beats PTQ at int4" is true for a model that actually goes through QAT, but the claim's described pipeline does not reproduce that and explicitly targets the degraded Q4_0 format, so the load-bearing conclusion does not hold. The supported alternative is to run QAT DURING the fine-tune and export via UD-Q4_K_XL (not naive Q4_0).

# RECIPE-DECISION BRIEF: Fine-Tuning the Coach LoRA on Gemma-4-26B-A4B (QAT question resolved)

## 1. RECOMMENDATION (one line)

**Keep your validated bf16 base (`unsloth/gemma-4-26B-A4B-it`) and do NOT swap to the QAT-unquantized checkpoint — STRONG (both QAT-path claims adversarially REFUTED).** The QAT advantage does not survive an ordinary bf16-LoRA-merge, and your intended Q4_0/int4 export is the single format Unsloth shows degrades worst (70.2% top-1); the base swap buys nothing and is contra-indicated by Unsloth's own docs.

## 2. Exact fine-tune entry point + load-flag changes

**Entry point: `unsloth/gemma-4-26B-A4B-it` — UNCHANGED from your validated recipe. Make NO load-flag changes.**

The QAT-unquantized checkpoint (`unsloth/gemma-4-26B-A4B-it-qat-q4_0-unquantized`) would *load* (identical `Gemma4ForConditionalGeneration` architecture, `dtype:bfloat16`, no `quantization_config`, ~51.6 GB safetensors), but:
- Its own model card scopes it to "custom downstream compilation and research," NOT fine-tuning.
- Unsloth's official fine-tuning guide (`unsloth.ai/docs/models/gemma-4/train`) points the LoRA base at `unsloth/gemma-4-26B-A4B-it`, never at the QAT repo.

Keep your validated flags verbatim:
```python
FastModel.from_pretrained(
    model_name      = "unsloth/gemma-4-26B-A4B-it",
    max_seq_length  = 2048,
    load_in_4bit    = False,   # MoE QLoRA blocked (bitsandbytes can't quant 3D fused experts)
    load_in_16bit   = True,    # bf16 LoRA
    full_finetuning = False,
)
```

**Do NOT add `qat_scheme=` to `get_peft_model`.** That is the *only* documented way to actually inherit QAT int4-robustness (fake-quant during training via torchao, then `quantize_(model, QATConfig(step="convert"))`). It is **untested on this 128-expert MoE** and its torchao-`int4` grid is **not confirmed to match the llama.cpp Q4_0/Q4_K_XL serving grid** you use. If you want to *experiment* with QAT, that — not the base swap — is the lever, but treat it as research, not the production recipe.

## 3. Export quant for serving: **UD-Q4_K_XL, not Q4_0**

**Decision: serve at Unsloth dynamic UD-Q4_K_XL. STRONG.**

The widely-cited "70.2% → 85.6%" number is the load-bearing trap: it is the cost of converting the QAT checkpoint to **naive Q4_0** (70.2% top-1), recovered to 85.6% (+15.6%) only by Unsloth's **dynamic UD-Q4_K_XL** method — which is also ~200 MB *smaller*. Unsloth ships exactly one GGUF per Gemma 4 model (UD-Q4_K_XL, ~14.2 GB for 26B-A4B) and states precisions *higher* than UD-Q4_K_XL also degrade accuracy. Q4_0 loses quality because llama.cpp uses F16 scales vs the model's BF16 scales.

GBNF contract: quant choice does **not** affect grammar-constrained decoding — `--grammar-file` operates on the sampler, independent of weight precision. So you pay nothing in JSON fidelity by choosing the higher-quality quant.

Caveat [med]: `save_pretrained_gguf` only exposes `quantization_method = q4_k_m | q8_0 | f16`. A *true* UD-Q4_K_XL requires running llama.cpp `quantize` with Unsloth's dynamic imatrix/tensor-type map manually. **Pragmatic path: export `q4_k_m` via Unsloth (close to UD-Q4_K_XL, far better than q4_0), and only build true UD-Q4_K_XL if smoke-test JSON quality is marginal.**

## 4. Chat template decision (adversarially SUPPORTED)

**Use the plain non-thinking `gemma-4` template (NOT `gemma-4-thinking`). Train==serve must match exactly.**

- Turn markers are Gemma 4's asymmetric tokens, NOT Gemma 3's: open `<|turn>`, close `<turn|>`. A turn renders `<|turn>{role}\n{content}<turn|>\n`; assistant role is literally `model`; `bos=<bos>`, `eos=<turn|>`.
- **26B-A4B-specific hazard:** even with thinking OFF, the 26B model still emits an **empty thought block** `<|channel>thought\n<channel|>` between `<|turn>model\n` and the JSON (only E2B/E4B skip it). `add_generation_prompt` injects this automatically.
- **Format your flat `{prompt, completion}` pairs so the JSON lands AFTER that empty block**, matching serve-time position:
  ```
  <bos><|turn>user\n{prompt}<turn|>\n<|turn>model\n<|channel>thought\n<channel|>{completion_json}<turn|>
  ```
- Do NOT inject `<|think|>` (that's the thinking-ON switch).
- Serve-time: disable thinking with `--reasoning off` (NOT `--reasoning-budget 0`, NOT `--chat-template-kwargs`, which were reported ineffective on 26B-A4B). Use `--grammar-file`, NOT `--json-schema` (the schema→GBNF path crashes sampler init on Gemma 4).

## 5. MoE / GB10 constraints

- **16-bit (bf16) LoRA — yes, still mandatory. QLoRA 4-bit remains BLOCKED.** bitsandbytes only quantizes 2D `nn.Linear`; Gemma 4 stores experts as fused 3D `nn.Parameter` (`experts.gate_up_proj [128,1408,2816]`, `experts.down_proj [128,2816,1408]`). QAT label changes nothing here — entry precision is BF16 either way.
- **LoRA target names: `experts.gate_up_proj` / `experts.down_proj` (note: NOT `mlp.experts.*`).** This is the PR #4913 fix (merged 2026-04-14, issue #4907). Verify your trainable-% is in the patched range — unpatched runs showed only 0.23% (r32) / 0.91% (r128) with experts silently unattached. Your ~1.88% figure is plausible *post-patch* but **unconfirmed by any source** — smoke-test it (§7).
- **Attention: `attn_implementation="sdpa"`.** FA2 caps head_dim at 256; Gemma 4 has 10 global layers at head_dim=512. (Note: the QAT card's `head_dim:256` is the sliding-window value; the 512 is the global-attention path — both exist.)
- **Memory: comfortably fits 121 GB.** Your ~77 GB peak at seq=2048 sits between published brackets (avenchat ~24 GB, Unsloth >40 GB; bf16 weights ~49 GB resident). **Keep peak under ~80 GB** — GB10 C2C interconnect hangs reported above ~80 GB (serving-side, but hedge).

**Decisive bottom line:** ship your existing bf16 recipe unchanged; reject the QAT-unquantized base swap; serve at UD-Q4_K_XL (or `q4_k_m` interim); the single highest-risk unknown to smoke-test is #1 (expert LoRA actually attaching post-PR-4913), and the single most valuable validation is #7 (the export→grammar-serve round-trip).
